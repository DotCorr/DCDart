# Compatibility matrix

Every Dart package/library touched, its compat tier, what broke, what was done. Populated from M5
onward (corpus sweep); kept here from the start so the format is settled before volume hits.

Tiers: T0 (byte-identical behavior) … T5 (does not work, documented why).

| Package/library | Tier | What diverged | Notes |
|---|---|---|---|
| `dart:core` / `dart:isolate` — shared-memory concurrency | n/a | **No upstream counterpart exists to diverge from.** Dart's concurrency model is isolates with no shared mutable memory, so upstream Dart has no atomics API at any layer — not in `dart:core`, not in `dart:isolate`, and `dart:ffi` never added one. | ADR-0055 (`Atomic.*`) and ADR-0056 (`fence(Ordering.…)`) are therefore pure DCDart extensions in `dc:core.bare`, not reimplementations. No upstream Dart program can call them and none can break on them. Recorded because the natural assumption — "surely `dart:ffi` has atomics" — is wrong, and a porting agent that assumes otherwise will look for a mapping that does not exist. |
| `dart:core` — `String.length` | **T3** | **`"héllo".length` is 6 in DCDart and 5 in upstream Dart.** Dart counts UTF-16 code units; DCDart's `Str.length` counts UTF-8 bytes. | ADR-0053. This is the largest deliberate semantic divergence in the language so far, and the most dangerous shape a divergence can take: **silently correct for pure ASCII, silently wrong at the first non-ASCII byte.** It will pass hand-written tests and fail in the field. `Str` is a distinct type (`extension type const Str(String)`) rather than an alias specifically so that `dart:core`'s `String.length` cannot be reached by accident — an earlier attempt exposed `.length` on plain `String` and the frontend resolved it to the upstream getter, returning code units, with no error anywhere. Asserted twice in `tests/conformance/str/`: at runtime, and on the emitted IR (a `[5 x i8]` global would mean the literal was *measured* in code units, not merely reported as such). |
| `dart:core` — function expressions and local functions (closures) | **T3** (was T4) | **A closure that CAPTURES anything is a compile ERROR, not slower code.** Upstream Dart closures capture their enclosing scope; DCDart lowers only the subset that captures nothing. `() => x + 1` inside a function taking `x` does not compile. What DOES work now, and did not on 2026-08-26 morning: a function can be **passed, returned, stored and called as a value** — `apply(f, x)`, `chooser(n)(x)`, a torn-off top-level or local function. So higher-order code in the `map`/`filter`/`fold` shape is reachable; `List.map` itself is not, for the unrelated reason that `List` has no such method yet. One restriction with no upstream counterpart: a callback's heap parameters must be BORROWED, because a Dart function TYPE has nowhere to write `@owned` (GAP-0057). | ADR-0057 + **ADR-0060**. Read with `docs/escalations/0008` open — **§2 (capture) is still the open half; §3 (elision) is answered.** **The performance claim this row used to make is withdrawn, and it was wrong in the pessimistic direction.** It said: "the honest expectation is that closures-as-values arrive slower than this row's subset, not equal to it", because an indirect call would lose `Call.argOwnership` and become an elision barrier. Measured after ADR-0060, on the same program written four ways (`examples/m3-funcptr`): `viaTopLevel`, `viaClosure`, `viaFuncPtr` and `viaTopFuncPtr` all emit `alloc=1 retain=0 release=0`. **A call through a function pointer is not slower than a direct call and elides the same `@owned` pair**, because ownership rides in the pointer's TYPE rather than being re-derived at the call site. The borrowed direction's pair correctly survives (`retain=1 release=2`), asserted in the same harness so the good number cannot come from a blanket elision. This row is the reason that measurement was worth doing before the benchmark existed: "closures are slow in DCDart" was on its way to being recorded here as a fact about the language when it was a fact about a missing analysis. |
| `dart:core` — generic CLASSES (`class Box<T>`) | **T2** | **Instantiation is a compile-time act with a symbol, not a runtime one.** Upstream Dart generic classes are reified: `Box<int>` and `Box<String>` share one class, one set of method bodies, and carry their type arguments at runtime, where `is`/`as` and `runtimeType` can see them. DCDart monomorphizes: `Box<u64>` and `Box<Node>` are separate emitted layouts, separate method bodies (`Box$u64_unwrap`, `Box$Node_unwrap`) and separate destructors, with no type argument surviving to runtime. | ADR-0054. Source-compatible for the code M3 needs — writing and using a generic container reads identically — so the divergence is in what a program can OBSERVE, not in what it can say. The three things that break are `runtimeType`, a type test against a type argument (`x is Box<T>`), and reflection over one; the first two do not exist in DCDart's subset and the third is escalation 0004. **Unbounded instantiation is a compile ERROR, not an infinite compile**: `f<T>` calling `f<Box<T>>` is legal upstream and rejected here, with the depth named. Also unlike upstream: generic METHODS on classes are not implemented at all (GAP-0055). |
| `dart:core` — object lifetime under ARC (reference reads and field overwrites) | **T1** | **A reference read is a strong `+1` for as long as the reading expression's value is live, and it holds even when the object is overwritten out from under it.** Upstream Dart is traced-GC: `final got = c.next; c.next = other; return got.n;` is unremarkable, because the collector keeps `got`'s object alive for exactly as long as `got` can reach it. DCDart reaches the same OBSERVABLE behaviour by a different mechanism — ADR-0017's alias retain plus ADR-0048's release of an overwritten field — so the source is portable and the reasoning underneath it is not. | **ADR-0063**, closing GAP-0054. Recorded here because for a period this row would have been **T4 and nobody knew**: elision pass 3 deleted the alias retain across the field overwrite, freeing the object while the reference was still live, and `dcc build` at `-O2` returned **198 where 110 is correct** (`examples/m3-elide-alias`). The reason it went unnoticed is the part worth carrying forward for the corpus sweep: cancelling a retain/release pair is refcount-NEUTRAL, so `dc_heap_live` read zero, every count balanced and there was no double free — **a leak test cannot see this class of divergence at all.** Any upstream package whose behaviour depends on a reference outliving a mutation of the structure it came from needs a VALUE assertion, not a heap assertion. Two costs remain and are not divergences from Dart, only from ideal codegen: ~4% on the `json` benchmark (GAP-0066), and a temporary passed to a borrowed parameter still leaking (GAP-0065). |
