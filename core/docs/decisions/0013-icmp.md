# ADR-0013: Implement ICmp (integer comparison)

**Status:** decided

## Context

`Result<T,E>`/`?` (GAP-0007) needs to test "is this Ok or Err" before branching — nothing in DC-IR
produces a `DCBool` from a runtime value. `core/dc-ir/instructions.dart`'s own header explicitly
scoped comparisons out ("None of these are needed to represent `a + b`") — no longer true now that
propagation needs one.

## Decision

Added `ICmp` to `core/dc-ir/lib/instructions.dart`: `dest` (`DCBool`), `predicate`
(`ICmpPredicate`: `eq`/`ne`/`ult`/`ule`/`ugt`/`uge`/`slt`/`sle`/`sgt`/`sge`), `lhs`/`rhs` (matching
`DCInt` types, no implicit widening — same rule as arithmetic). Predicate names match LLVM's own
`icmp` condition codes exactly (`core/backend/lib/llvm_emit.dart` just prints `predicate.name`, no
translation table) — signed vs. unsigned ordering comparisons are genuinely different operations
(spec §4.1's sized integers are always definitively signed or unsigned), so the split mirrors a real
distinction, not an arbitrary naming choice.

**Verified independent of dcc-lower** (same discipline as ADR-0012): a hand-built `maxOf(u64,u64)`
`DCFunction` (`icmp ugt` → `CondBranch` → direct return in each arm, no merge/phi needed for this
shape) produced correct LLVM IR, compiled, linked, and ran correctly for 4 cases — including the
critical unsigned-vs-signed edge case (`maxOf(1, 0xFFFFFFFFFFFFFFFF)` must return the huge value, not
treat it as `-1`). Confirmed still freestanding when compiled for the ELF target.

## Consequences

`core/dcc-lower` still does not produce `ICmp`/`CondBranch` from real DCDart source — nothing
recognizes a Dart conditional or a Result-tag check yet. This ADR proves the primitive; GAP-0007
tracks what's still needed to use it.
